# Stable Desk v3 hosted setup checklist

October 1, 2026. Setup is pending approval. Original local review commit `57558190ee86d9f718e3a03b872d786ce105763e` is preserved; use its modern-key follow-up for the recommended setup. No resource, account, credential, grant, push or deployment is created by these instructions.

1. **Confirm the approved backend.** Prefer a dedicated Supabase Free project, or identify an existing isolated test project with no unrelated data. An existing authorized Owner/Admin can perform setup; no new team invitation, management token, Supabase–Vercel OAuth integration or broad GitHub grant is required by this architecture. Any such prompt needs separate review. [Supabase access roles](https://supabase.com/docs/guides/platform/access-control).
2. **Approve the database change.** Inspect existing objects before applying `db/001-pilot.sql`. It creates `stable_desk_v3`, `stable_desk_v3_recovery`, `stable_desk_v3_write`, owner-read RLS policies and server-only write grants. Stop at an unexpected name collision rather than overwriting another application. No production database copy or existing-table migration is required.
3. **Approve one project-scoped identity.** Reuse an approved Auth account already belonging to this test project. A new project needs its own test user; account/password creation requires explicit approval and a secure provider workflow. No signup, invitations, social login, email delivery or password transmission in chat is needed by the app.
4. **Configure through secure settings.** Use `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY` and `PILOT_OWNER_ID`, only on the approved Vercel preview branch. All are absent here. Legacy JWT names `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY` are fallbacks only when the corresponding modern name is absent. Empty/invalid modern values stop configuration instead of selecting an old key. No public/client prefix, source commit, export or chat message may carry the privileged value.
5. **Confirm the existing Vercel target.** Reuse the current Stable Desk project, keep production at its existing commit, and preserve preview access protection. An authorized existing project maintainer needs permission to set preview environment values and deploy that preview. Do not change organization roles or obtain new permissions implicitly. Vercel Authentication supports every plan; no paid password-protection add-on or bypass link is required. [Deployment protection](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/vercel-authentication).
6. **Verify before adoption.** Inspect the actual preview commit, server-function packaging and build result. Exercise real password login/logout/expiry, unauthorized users, owner read isolation, concurrent writes/recovery, cross-device continuation, source reachability/extraction, first dated baseline, candidate staging, accepted/rejected evidence and weekly brief. Export local v2 first and explicitly copy only into an empty shared account. Production rollout and any schedule still require separate approval.

## Published limits and permissions

[Supabase Free pricing](https://supabase.com/pricing), checked October 1: $0/month, two active projects, 500 MB database per project, 5 GB egress and 50,000 MAU. Projects pause after one week of inactivity; automatic backups and point-in-time recovery are excluded. These published limits do not establish available account capacity, existing plan eligibility or a guaranteed bill. Measure database/recovery size and retain independent exported backups. Stop rather than upgrade automatically.

The application's smaller operational bounds remain 60 committed operations, 4 MB current state, one manually triggered source check per minute, an eight-second source timeout and a 1 MB response limit. These are not provider billing guarantees. No recurring collector, scheduled delivery or paid API is enabled.

[Vercel Hobby](https://vercel.com/docs/plans/hobby) is restricted to personal, non-commercial use. Confirm the actual existing plan, usage and intended use before activation; if an upgrade is required, stop for approval. Creating a second project does not resolve that requirement.

## Key compatibility and security boundary

[Supabase's migration documentation](https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys) recommends publishable/secret keys and states legacy-key deprecation by the end of 2026. Modern API keys are not user JWTs. The adapter sends modern secrets only in `apikey`; Auth uses the publishable key plus a separate user's bearer when needed. Legacy JWT transport remains supported for existing configurations. No key rotation, legacy-key deactivation, provider JWT-verification change or OAuth authorization is part of this code update.

Modern secrets and legacy service-role keys bypass RLS across their project. The server must still verify the user with the provider, enforce its approved account and derive the owner before privileged storage calls. That boundary is implemented and tested locally; a dedicated project limits the consequences of credential misuse. Do not place unrelated/private records in this pilot. Provider behavior is still a hosted acceptance gate; request stubs and PostgreSQL fixtures are not proof of live security configuration.

Configuration shape checks select transport; they do not validate a key's signature, role, project membership or validity. The public `configured` status means the server settings have the supported shapes, not that the provider connection is healthy. Real gateway and account verification must pass during hosted acceptance.
